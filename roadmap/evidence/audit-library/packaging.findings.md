# packaging

## Summary
Build, packaging, tests and docs are not ready yet for a stable multi-framework release. Several of the problems break things users do routinely. First, the `data` property setter throws on 9 of the 17 components, because those subclasses override only `get data()`. I confirmed the TypeError by running the code in memory. Second, the React 19 and Vue wrappers pass already-serialized JSON into that property, so it gets encoded twice: the other 8 charts render empty and the 9 throw. Third, the Angular adapter is just Vite-transpiled decorated classes with no Ivy partial compilation, so Angular apps compiled ahead of time can't use it. On top of that, 1.4.0 removed element registration from `MiniChartDirective`, which the README example relies on. That change shipped as a minor release even though it breaks code.

CI runs on Forgejo while the origin remote is GitHub. It runs tests before the build, but test/components.test.js imports `dist/`, so the suite fails on a clean checkout (reproduced locally). It also deploys the live demo from any branch with a non-atomic `rm -rf` and copy. There's no release workflow and no `prepack` build. The v1.4.0 tag is missing and the CHANGELOG lists a 1.3.1 that was never released.

The exports map matches the 24 Vite entries one-to-one. But the type paths for the 17 component subpaths and `./math` almost certainly point at .d.ts files the build doesn't emit, since vite-plugin-dts mirrors the src tree; the author worked around this only for the adapters. The same declaration file also serves both the ESM and CJS entries, and the CJS build doesn't add much for browser-only custom elements on Node 22+. Marking only register and react as `sideEffects` matches the code, but it comes from React's eager registration at import, which pulls all 17 charts into every React bundle. `./math` freezes the internal geometry functions as public API, exposed twice. The TypeScript toolchain (TS 7 native plus an unused `@typescript/typescript6` plus vite-plugin-dts 5) is fragile for generating declarations from JSDoc.

The 30 tests cover pure geometry and part counts on a hand-written fake DOM. Events, re-rendering, the `data` property, accessibility, theming tokens, adapters, built bundles and types are untested, and there's no coverage, browser, visual or size tooling. Two contract drifts already show it: `slice-select` is declared by every adapter but dispatched by nothing, and React silently drops its typed event props. The docs contradict the code in many places: Svelte bindings that don't exist, Vitest, wrong token defaults, color-1..8 versus about 50 real tokens, missing demo files, and a GitHub username in package.json that doesn't match the git remote. The geometry module itself handled all 18 edge cases I tried.

## Findings

### [critical] packaging-1: `el.data = …` throws TypeError on 9 of 17 components because subclasses override only the getter (bug)
- Evidence: src/core/mini-chart-element.js:43-51 (base get/set data); getter-only overrides at src/components/mini-bullet-chart.js:69, mini-candlestick-chart.js:69, mini-combo-chart.js:79, mini-ohlc-chart.js:61, mini-radial-bar-chart.js:78, mini-range-bar-chart.js:68, mini-scatter-chart.js:70, mini-stacked-area-chart.js:74, mini-stream-chart.js:73. Consumers: src/angular/mini-chart.directive.ts:104 (and the same `el.data = d` in all 18 directives). Docs promise it: README.md:37 'Synchronized HTML data / label attributes and JavaScript properties'.
- Detail: In JS a class that defines only `get data()` shadows the parent's accessor pair, so the setter disappears. ES module code runs in strict mode, so assigning throws. I checked this in memory: I stubbed HTMLElement, imported src/index.js and assigned `el.data = [[1,2,3,4]]` on every class. It threw `TypeError: Cannot set property data of #<MiniBulletChart> which has only a getter` for Bullet, Candlestick, Combo, OHLC, RadialBar, RangeBar, Scatter, StackedArea and Stream. The property API is therefore broken for half the library, and every Angular directive for those 9 charts throws inside its effect. No test ever uses the setter: components.test.js only calls setAttribute. Related gap: the base class has no lazy-property upgrade (`hasOwnProperty('data')` re-set in connectedCallback). A property set before customElements.define becomes an own property and shadows the accessor for good.
- Rec: Keep a single accessor pair in MiniChartElement and give subclasses a `parseData(raw)` hook (or a static schema) instead of letting them override `data`. Have the setter accept arrays/objects and pre-serialized strings. Add the upgrade-property pattern for `data` and other properties. Add a table-driven test over all 17 classes that round-trips property to attribute to render.

### [critical] packaging-2: React 19 and Vue wrappers pass JSON strings into the `data` property: double-encoded (empty chart) or TypeError (bug)
- Evidence: src/react/index.ts:217 (element defined at import), :231-235 `data: typeof data === "string" ? data : JSON.stringify(data)`; src/vue/index.ts:43 (defined in setup), :48 same stringify; adapter test only checks `typeof` at test/components.test.js:392-401.
- Detail: On the client, React 19 assigns custom-element props as properties when `name in node`. Vue's runtime-dom `shouldSetAsProp` does the same `key in el` check. Both wrappers register the element before rendering, so `data` already exists on the instance and the pre-stringified JSON goes into the setter, which stringifies it again. I verified `el.data = "[1,2,3]"` gives the attribute `"\"[1,2,3]\""`, which parses to `[]`. Result: the 8 components with the base setter render empty, and the 9 getter-only components throw. React 18 sets attributes, so it happens to work there; React 19 is the devDependency and the version the README advertises. The tests can't catch this because they only assert `typeof === 'object'`.
- Rec: Pass raw arrays/objects as properties (React 19 and Vue both support this) and make the element setter accept both arrays and strings. For React 18, set the property through a ref/effect. Add render tests: @testing-library/react on a React 18 + 19 matrix and @vue/test-utils, both in happy-dom, asserting the rendered SVG part counts.

### [critical] packaging-3: The Angular adapter ships as Vite-transpiled decorated classes with no Ivy partial compilation, so AOT Angular apps can't use it (packaging)
- Evidence: vite.config.js:34 (angular entry built by Vite/rolldown); tsconfig.json:7 `experimentalDecorators`; src/angular/mini-chart.directive.ts:78-118 (signal `input()`/`output()` in @Directive); package.json:177-186 (no @angular/compiler-cli / ng-packagr); test/components.test.js:404-410 only checks `typeof === 'function'`.
- Detail: Angular apps compile libraries from their .d.ts metadata (`static ɵdir: ɵɵDirectiveDeclaration`, `ɵfac`) and link `ɵɵngDeclareDirective` partial output. A plain class run through `__decorate(Directive(...))` has neither. In an AOT build, `imports: [MiniLineChartDirective]` is rejected as not standalone. At runtime the decorator needs `@angular/compiler` for JIT, and signal inputs are only recognized by the compiler, so `[data]` bindings fail. Also, 1.4.0 removed element registration from `MiniChartDirective` (current :842-859 vs v1.3.0, whose constructor called defineMiniChart). The README Angular example (README.md:168-185, getting-started.md:117-135) imports only that directive, so its tags never upgrade. The CJS build of an Angular adapter (`dist/angular.cjs`) has no consumer.
- Rec: Build the Angular adapter with ng-packagr (APF, partial compilation): a separate package such as @sparkline-mini-charts/angular, or a secondary entry point. Set the peer range to match the compiler major used, ESM only. Add CI fixtures for an Angular CLI app at the minimum and latest supported majors, running `ng build` (AOT) and `ng test`. Restore registration in MiniChartDirective or document the breaking change.

### [high] packaging-4: Tests import built `dist/` but CI runs tests before build: the suite fails on a clean checkout (testing)
- Evidence: test/components.test.js:387-389 imports ../dist/react.js, ../dist/vue.js, ../dist/angular.js; .forgejo/workflows/ci.yaml:22-29 order is typecheck, test, build; .gitignore:4 ignores dist/. Ran locally: `node --test test/components.test.js` gives ERR_MODULE_NOT_FOUND .../dist/react.js (11 pass, 1 fail).
- Detail: This test was added in 5a9322d (v1.4.0). checkout@v4 cleans the workspace by default (`git clean -ffdx`), so dist/ is absent when `pnpm run test` runs. CI should be red since v1.4.0, and the self-hosted demo deploy (after the test step) is blocked. Vercel (vercel.json:3) skips tests and deploys anyway, which hides the failure. The test also mixes unit tests of src with integration tests of built artefacts, and it needs react/vue/@angular/core installed.
- Rec: Split the suites: `test:unit` (src, no build) and `test:package` (dist plus the packed tarball), and order CI as build, then package tests. Better, test the adapters with real renderers (see the adapter-tests finding) rather than importing dist.

### [high] packaging-5: Types for 18 of 24 subpath exports point at .d.ts files the build doesn't emit (verify with build + attw) (packaging)
- Evidence: package.json:35-126 `types: ./dist/mini-*.d.ts` and `./dist/math.d.ts`; vite.config.js:16-33 entries come from src/components/*.js and src/core/geometry.js; vite.config.js:49-53 `dts({ include: ['src'], outDir: 'dist', rollupTypes: false })` with no insertTypesEntry/entryRoot; src/react.ts:1 comment 'stable top-level declaration path' (workaround applied only to adapters).
- Detail: With rollupTypes false, vite-plugin-dts/unplugin-dts mirrors the source tree under entryRoot=src. Declarations land at dist/components/mini-line-chart.d.ts and dist/core/geometry.d.ts. Per-entry stub d.ts files are only written when `insertTypesEntry` or `rollupTypes` is on. The author already hit this for the adapters and added src/react.ts, src/vue.ts and src/angular.ts as top-level shims, but not for the 17 component subpaths or `./math`. TS consumers of README 'Mode 3' (`import { MiniLineChart } from 'sparkline-mini-charts/mini-line-chart'`) will likely get TS7016 (no declaration file). I couldn't build (node_modules absent, read-only), so confirm with `pnpm build && ls dist/*.d.ts`.
- Rec: Use `output.preserveModules` with entries whose paths match the export paths, or turn on per-entry type stubs (insertTypesEntry), or move to tsdown, which generates dts per entry. Add `attw --pack` and `publint` to CI so exports/types mismatches fail the build.

### [high] packaging-6: No release pipeline: publishing can ship an empty package, tags are manual and incomplete (packaging)
- Evidence: package.json:149-162 (files ['dist'], no prepack/prepublishOnly); .gitignore:4 (dist ignored); git tags: v1.0.0, v1.0.1, v1.1.0, v1.2.0, v1.2.1, v1.3.0 (no v1.4.0, no v0.1.0); package.json version history 1.3.0 then 1.4.0 (d46ddc6 to 5a9322d), yet CHANGELOG.md:22 and README.md:248 document a [1.3.1] that was never versioned.
- Detail: Nothing builds before `npm publish`, so a publish from a fresh clone ships a tarball with only README/CHANGELOG/LICENSE. There's no workflow for versioning, tagging, GitHub releases, npm provenance or dist-tags, and the release history in git doesn't match the CHANGELOG.
- Rec: Add `"prepack": "pnpm build"`. Adopt Changesets: a version PR, then `changeset publish` in a release workflow on main using npm trusted publishing (OIDC) with `--provenance` and automatic tags/GitHub releases. Reconcile the CHANGELOG (remove or annotate 1.3.1) and tag v1.4.0 retroactively.

### [high] packaging-7: v1.4.0 shipped breaking changes as a minor release (api)

Adopt a written semver/deprecation policy, require a 'Changed/Removed/Breaking' section via changesets, and guard the public API with api-extractor reports (or attw plus type tests) so breaking diffs fail CI. Move demo/site notes out of the package CHANGELOG.

### [high] packaging-8: CI deploys production from every branch push, non-atomically; CI lives on Forgejo while origin is GitHub (ci)
- Evidence: .forgejo/workflows/ci.yaml:3-4 (`on: push`, no branch filter, no pull_request), :34-38 (`rm -rf /deploy/sparkline-mini-charts/*` then `cp -a`), :43 (`ls -la /deploy` dumps the host volume to logs); no `concurrency`; `git remote -v` gives git@github.com:ErlonRr/sparkline-mini-charts.git with no .github/workflows.
- Detail: Any feature-branch push overwrites the live demo. The rm-then-copy leaves a window with an empty or partial site, and an interrupted copy leaves it broken. Two concurrent pushes can interleave. GitHub, the canonical remote, runs no CI at all, so PRs there get no checks. There's no lint, size budget, publint/attw, or Node/browser matrix.
- Rec: Trigger on pull_request plus push to main, with `concurrency: { group: ${{ github.ref }}, cancel-in-progress: true }`. Deploy only from main after all checks pass, atomically (build into a temp dir, then `mv`/symlink swap), or keep one deploy target (Vercel previews per PR, production on main). Mirror the pipeline to GitHub Actions if GitHub is canonical.

### [high] packaging-10: Public types aren't generated from one source: attribute/event types drift, framework typings are missing (typing)
- Evidence: React prop types diverge from runtime: src/react/index.ts:172 `mode?: 'win-loss' | 'uptime'` vs src/components/mini-win-loss-chart.js:185 accepting only 'status'; src/react/index.ts:51 `curve` omits 'step-after'/'step-before' accepted at mini-line-chart.js:237. src/react.ts:3-22 re-exports only `MiniChartProps`, so the 17 per-chart Props interfaces in src/react/index.ts:50-201 aren't importable. src/vue/index.ts:27-40 types only data/label/interactive as `PropType<any>`. src/core/mini-chart-element.js:43-49 `data` is `any[]`. No HTMLElementTagNameMap, JSX IntrinsicElements, Vue GlobalComponents or custom-elements.json anywhere (grep empty). Events are untyped `CustomEvent`.
- Detail: Attribute metadata lives in three hand-maintained places: observedAttributes arrays in each component, React interfaces, and Angular inputs (src/angular/mini-chart.directive.ts). They already disagree. TS users of the raw elements get no attribute/event typing, Vue users get no prop checking for chart-specific attributes, and Svelte/Solid/Preact/Lit users get nothing. For a multi-framework web-component library, the Custom Elements Manifest is the standard input for all of these integrations.
- Rec: Define a per-component schema (attributes: type/default/parse/reflect; properties; events with detail type; CSS parts; CSS custom properties). Generate observedAttributes, the adapters, `custom-elements.json` (via @custom-elements-manifest/analyzer or a custom generator), HTMLElementTagNameMap/JSX/Vue/Svelte type augmentations and the docs tables from it. Add type tests (vitest --typecheck / expect-type).

### [medium] packaging-11: React entry is side-effectful (eager registration), defeating tree-shaking; Vue/Angular factories lack PURE annotations (perf)
- Evidence: package.json:143-148 sideEffects lists register.* and react.*; src/react/index.ts:217 `defineMiniChart(...)` runs inside each top-level `createReactChart(...)` call (:279-327); src/vue/index.ts:67-115 and src/angular/mini-chart.directive.ts top-level factory/decorator calls without `/* @__PURE__ */`; test/package.test.js:47-53 locks the current list.
- Detail: The list is consistent with the code: register and react have module-level effects, while define/vue/angular/components don't. Vue registers lazily in setup (src/vue/index.ts:43), which is the better design. But importing one React wrapper evaluates all 17 `createReactChart` calls, so every element class is bundled. For Vue, `export const X = createVueChart(...)` calls can't be dropped by bundlers unless the factory is annotated, so importing one wrapper likely retains all 17. Root-index users in unbundled ESM (CDN, import maps, Vite dev prebundle) evaluate all 17 component modules just to get `defineMiniChart` (README.md:86-89).
- Rec: Register lazily (first render / ref callback / Angular constructor) and annotate factories with `/* @__NO_SIDE_EFFECTS__ */` or `/* @__PURE__ */`. Then sideEffects can be just `["./dist/register.*"]`. Offer per-component adapter subpaths and self-registering leaf entries (e.g. `sparkline-mini-charts/mini-line-chart/define`). Enforce with size-limit per entry.

### [medium] packaging-12: `./math` and the root index expose all 19 internal geometry symbols as public API; the base class isn't exported (api)
- Evidence: vite.config.js:33 `math: src/core/geometry.js`; package.json:120-126; src/index.js:24-44 re-exports the same 19 symbols (TAU, createBarLayout, … polarToCartesian); src/core/geometry.js exports at :3-749; MiniChartElement not exported from any entry.

Meanwhile the extension point users would want (MiniChartElement, chartStyles/token defaults, event types) isn't public.

### [medium] packaging-13: Fragile TypeScript toolchain: TS 7 native + unused @typescript/typescript6 + vite-plugin-dts 5 bound to typescript@7 (dx)
- Evidence: package.json:178 `@typescript/typescript6: ^6.0.2` (referenced by no script or config), :182 `typescript: ^7.0.2`, :184 `vite-plugin-dts: ^5.0.3`; pnpm-lock.yaml:1120-1131 unplugin-dts resolved with `typescript: 7.0.2`; pnpm-lock.yaml:833-835 @typescript/typescript6 is an alias of typescript@6.0.3.
- Detail: Declaration emission from JSDoc depends on the TS compiler JS API. The native TS 7 package isn't API-compatible with the classic API, which is presumably why the typescript6 shim was added, but nothing wires it in. The dts plugin may produce degraded output or nothing, and with no attw/publint in CI nobody would notice. If Angular moves to ng-packagr, its compiler-cli also pins a TS range.
- Rec: Either keep TypeScript 6 for emit (API consumers) and use tsgo only for `typecheck`, or migrate core to .ts with `isolatedDeclarations` and tsdown/oxc dts. Remove unused deps (knip). Verify dts output in CI with attw.

### [medium] packaging-14: tsconfig mixes dts-emit and typecheck roles; JS output target is implicit; real browser floor is undocumented (packaging)
- Evidence: tsconfig.json:3-16 (`emitDeclarationOnly`, `noEmit:false`, `experimentalDecorators` global, `target/lib ES2024`, `include: ['src']`); package.json:161 `tsc --noEmit`; vite.config.js:10-47 no `build.target`; color-mix() at src/components/mini-bullet-chart.js:108-110 and mini-scatter-chart.js:104.
- Detail: `target: ES2024` affects only type checking, because Vite/Oxc ignores it and uses the default `build.target` ('baseline-widely-available').

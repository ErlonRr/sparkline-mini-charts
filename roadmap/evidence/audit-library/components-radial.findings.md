# components-radial

## Summary
I read all five radial/part-to-whole components in full (pie 232 LOC, half-pie 227, gauge 417, progress 310, radial-bar 374, about 1,560 LOC in total), plus geometry/svg/data/palette/registration, their docs, the component tests and the React/Vue/Angular wrapper code that touches them. None of the five uses the base `MiniChartElement.render()`. Each one has its own DOM bootstrapping, listener plumbing, gradient parsing and initial-animation trick, and those tricks come in five different styles: a mask plus setTimeout, a double rAF, a forced reflow plus setTimeout, and one entrance animation in progress that is dead code. Pie and half-pie are about 85% identical (only 39 diff lines). The gradient parsers in gauge and progress are byte-identical except for their hard-coded defaults.

Several bugs break behaviour in normal use. All five lose their interactive events after a disconnect and reconnect, because `cleanup()` detaches the listeners and the "create once" branch never adds them back. Radial-bar leaves ghost rings on screen when the data array shrinks. Progress makes its value arc invisible when `gradient="false"`, which is exactly what Vue 3 and the Angular `syncJsonAttr` send for a false binding. Progress also fires `progress-complete` on every re-render. Some boolean attributes can't be turned off from React or Angular: `round-caps` is on by default and only the literal string "false" disables it.

The data structures are weak. The base parser silently drops invalid entries, which shifts indices and therefore colours. For gauge it shifts the positional `[value,min,max]` meaning too, and the docs contradict each other on what gauge's data even is. Negative and zero-sum inputs produce a blank chart with no empty state. The geometry has precision problems: a dominant slice above about 99.9998% vanishes because both arc endpoints round to the same point, and radial-bar `sweep` is never validated.

Theming is not consistent. Colours reach the SVG in three different ways: an inline per-index custom property (pie), an inline `style.stroke` (radial-bar) and an SVG presentation attribute (gauge zones). `--mini-chart-stroke-width` defaults to 14 for gauge, 12 for progress and 2 for lines, so setting it globally breaks the gauge and progress charts. The default gradients are hard-coded hex values that no token can change, and hover events report palette hex values even when the theme overrides the colour. The docs have drifted a long way: wrong part names (`slice`, `zone`), two attributes that are documented but do nothing (`pad-angle`, radial-bar `min`), wrong defaults, and a README `--mini-chart-fill` example that has no effect on pie. The test mock DOM can't detect any of these problems.

## Proposals
- Unify the radial family on one stateful base and controllers. Add a `StatefulChartElement` (skeleton created once, an `update(state)` hook, listeners attached once, cleanup limited to timers and rAF), composed with shared controllers: `GradientController` (one parser, signature-cached `<linearGradient>`, deterministic ids), `InteractionController` (pointer plus roving-focus keyboard, throttled, one event schema with resolved colours), `RevealAnimation` (Web Animations API, honours prefers-reduced-motion, cancellable). Merge pie and half-pie into a single `RadialPartChart` parameterised by `start-angle`, `sweep`, `inner-radius` and `pad-angle`, keeping `mini-half-pie-chart` as a thin preset subclass.
- Build a typed data layer to replace silent filtering. `normalizeSeries(input) -> { items: Array<{ value, label?, color?, valid }>, total, issues }` keeps index alignment and accepts `number | {value,label?,color?}` for pie, half-pie and radial-bar. `normalizeMeter(input, attrs) -> { value, min, max, clamped, overflow }` accepts `number | [number] | {value,min?,max?}` for gauge and progress. Add one shared `resolveDomain()` with a documented policy (meters default to 0..100, data-relative only with `max="auto"`, and min ≥ max is a dev warning plus a swap). Deprecate the positional `[value,min,max]`, with a migration note.
- Harden the radial geometry. describePieSector and describeArc should split arcs over 180° in two (so the endpoints never coincide), derive the sweep flag from the sign of the sweep, clamp sweeps, and implement pad-angle. createRadialBarLayout should compute ring width and step together, take a min, guard max ≤ 0, and avoid spreading into Math.max. Add property-based tests for extreme ratios, 0%, 100%, >100%, a single full circle and zero-sum data. Add an explicit empty or zero-sum track state as a geometry output.
- Write a theming specification with three tiers. (1) Global tokens defined once in a shared constructable stylesheet: `--mini-chart-color`, `--mini-chart-palette-1..N` (CSS is the source of truth for the palette, with JS reading resolved values for events), `--mini-chart-track-color`, `--mini-chart-text-color`, semantic `--mini-chart-safe/warn/danger-color`, and motion tokens. (2) Component-scoped tokens that never collide: `--mini-gauge-track-width`, `--mini-progress-track-width`, `--mini-radial-track-width`, `--mini-pie-gap-*`. (3) Indexed `::part`s everywhere (`segment-N`, `zone-N`, `ring-N`, `value`, `track`). Rule: JS only writes per-element custom properties inline, never stroke, fill or transition, so tokens and ::part always win. Build default gradients from tokens.
- Generate the API contract from one manifest. A `custom-elements.json` (or a small `meta.js` per component) lists every attribute (type, default, reflect, boolean semantics), property, event (name plus detail type), part and CSS property. Generate the React, Vue and Angular wrappers, the TypeScript types and the docs/components/*.md pages from it. That removes the phantom `slice-select`, the missing `progress-complete`, the dropped React handlers, the unused `pad-angle` and `min`, and the doc drift. Add one `parseBoolAttr` and typed reflecting properties so wrappers can set `el.roundCaps = false` instead of guessing at attribute strings.
- Define an event and state contract. Events are namespaced and edge-triggered (`sparkline-hover`, `sparkline-leave`, `sparkline-select`, `sparkline-change`, `sparkline-complete`, `sparkline-zone-change` with previous and current state), and none fire during the initial connect unless a property requests it. Every hover detail shares `{index, value, raw, percent (0..1), color (resolved), label?}`. Value display goes through `Intl.NumberFormat` (`locale`, `format`, or a `valueFormatter` property).
- Adopt a real-DOM test strategy: happy-dom or linkedom unit tests per component with a shared edge-case matrix (empty, single, NaN or strings, negatives, all-equal, 10k items, min>max, attribute removal, reconnect, data shrink, boolean "false"), Playwright visual and animation checks for reveal, needle and dash animations under reduced motion, and a smoke test that renders every docs example and asserts that no attribute named in the docs is unobserved.

## Findings

### [high] components-radial-1: Interactive events stop working after a disconnect and reconnect (all 5 components) (bug)
- Evidence: pie:49-55 cleanup() calls #detachInteractionListeners(); pie:65-90 reattaches (#setupInteractionListeners at :89) only inside `if (!svg || !style)`, which is false on reconnect. Same pattern in half:47-53/63-87, gauge:96-102 + 108-110 (#createDOM only when !#initialized; setup at :202), progress:66-72 + 78-80 (setup at :165), radial:66-72 + 96-98 (setup at :147).
- Detail: Moving a chart in the DOM fires disconnectedCallback and then connectedCallback. Examples: React keyed list reorders, Vue <KeepAlive>/<Teleport>, Angular CDK drag-drop, or a plain appendChild of an element that is already connected. On disconnect, cleanup() removes the pointer listeners from the internal SVG nodes. On reconnect, render() takes the 'already initialised' branch, so the listeners are never attached again. CSS :hover still works but sparkline-hover and sparkline-leave never fire again. The listeners sit on shadow-internal nodes that live exactly as long as the host, so detaching them was never needed.
- Rec: Attach interaction listeners once, when the DOM skeleton is created, and never detach them (the shadow nodes are garbage-collected with the host). Alternatively, attach them in connectedCallback and detach in disconnectedCallback symmetrically. Limit cleanup() to timers and rAF. Add a reconnect test that uses a real DOM.

### [high] components-radial-2: Radial-bar leaves stale 'ghost' rings when the data array shrinks (bug)
- Evidence: radial:253-276 only grows #tracks (`while (this.#tracks.length < tracks.length)`); the update loop radial:337-371 iterates `tracks.forEach` over the new length only. Extra caches are hidden only when data is completely empty (radial:225-229).
- Detail: Suppose the data goes from 4 values to 2. The update rewrites rings 0 and 1, recomputing their radii for n=2, while rings 2 and 3 stay visible with their old arcs, colours and data-track-index. The chart then shows wrong data and overlapping rings, and hovering a ghost ring dispatches sparkline-hover with `value: 0` because #currentData[2] is undefined. This happens in ordinary live-data use.
- Rec: After the update loop, remove the surplus caches together with their gradients (`this.#tracks.splice(n).forEach(t => { t.group.remove(); t.gradient.remove(); })`), or at least hide them. Better still, use a keyed reconcile helper shared by every multi-item component.

### [high] components-radial-3: Progress: gradient="false" or any unparsable gradient value makes the value arc invisible (theming)
- Evidence: progress:110-112 `:host([gradient]) [part="value"] { stroke: unset; }` matches any presence of the attribute; progress:207 returns null for "false" and progress:274 then clears the inline stroke. Angular: mini-chart.directive.ts:42-50 syncJsonAttr serializes `false` as "false" (used for progress at :441). Vue 3 passes `:gradient="false"` through attrs as gradient="false" (vue/index.ts:47).
- Detail: `stroke` is an inherited property, so `unset` behaves like `inherit`, which resolves to `none` from the svg. When JS decides there is no gradient (value "false", or a value such as "blue" that is neither JSON nor a CSV list, which also returns null at progress:219), nothing restores the stroke and the progress arc disappears. Binding `[gradient]="false"` in Angular or `:gradient="false"` in Vue is the normal way to turn the option off, and it is exactly the case that breaks.
- Rec: Don't key CSS on the bare presence of a value-carrying attribute. Toggle a class or data-state from JS once the gradient has been resolved (e.g. `svg.dataset.gradient = 'on'`), or set the stroke only through the inline style or a custom property. Add one shared `parseGradientAttr()` that treats "false", "0" and "" consistently.

### [high] components-radial-4: Progress entrance animation is unreachable code (bug)
- Evidence: progress:152 sets the `stroke-dashoffset` *attribute*, but progress:277 checks `this.#valuePath.style.strokeDashoffset === "100"` (the inline style, which is "" on first render), so isInitial is always false; the double-rAF block at progress:279-295 never runs. The docs promise 'a robust, bouncy entrance animation' (docs/components/mini-progress-chart.md:3).
- Detail: On first render the else-branch (progress:296-300) sets the transition and the target offset in the same task that created and appended the path. There is no earlier computed style for the browser to transition from, so the arc simply appears in its final state. `dataset.rendered` is never set either. The test mock's `style` is a plain object, so this goes unnoticed.
- Rec: Track the initial state with a private boolean field instead of inferring it from styles. Better, replace all the ad-hoc initial-animation code with one shared helper based on the Web Animations API (`el.animate(...)`, honouring prefers-reduced-motion and returning a cancellable handle).

### [high] components-radial-5: Boolean attributes can't be reliably turned off from frameworks (round-caps, show-value, interactive) (api)
- Evidence: radial:112 `roundCaps = getAttribute("round-caps") !== "false"` (default ON, read only in #createDOM). React drops false booleans: react/index.ts:258-260 `if (val) domAttributes[kebabKey] = ""`; Angular maps false to removal: mini-chart.directive.ts:375 + :395. gauge:319 / progress:250 use `hasAttribute("show-value")`; Vue 3 renders `:show-value="false"` as show-value="false".
- Detail: `round-caps` is effectively on unless the string "false" is present. React (`roundCaps={false}`) and Angular (`[round-caps]="false"`) both remove the attribute, so caps stay round; in those frameworks butt caps are impossible. Because the value is read once into the stylesheet, toggling it at runtime does nothing even in plain HTML. Meanwhile `show-value="false"` and `interactive="false"` count as true. The library has no single boolean contract, so each wrapper guesses.
- Rec: Define one `parseBoolAttr(value, default)` and document the HTML rule that presence means true. Replace default-on booleans with an enum (`caps="round|butt"`) or an inverse flag (`flat-caps`). Rebuild dynamic CSS (or set a `data-caps` attribute and select on it) when the attribute changes. Back each attribute with a typed, reflecting property so wrappers can set `el.roundCaps = false`.

### [high] components-radial-6: progress-complete fires on every render, not when the value crosses max, and no wrapper exposes it (api)
- Evidence: progress:302-308 dispatches whenever `clampedVal >= max` inside #updateChart, which runs for every observed attribute change (label, unit, show-value, gradient, interactive) and on reconnect. vue/index.ts:41 emits list lacks it; Angular progress directive (mini-chart.directive.ts:409-446) has no output; React handler props (react/index.ts:31-36) lack it.
- Detail: With `data="[100]"`, changing the label or toggling `interactive` re-fires 'complete'. Reconnecting fires it again. The event also fires synchronously during the first connectedCallback, before most consumers have attached a listener, so plain HTML users miss the one event they care about. Framework users have no typed hook for it at all.
- Rec: Make the event edge-triggered by tracking the previous completion state and dispatching only on the false-to-true transition, optionally also on true-to-false. Rename it into the shared namespace (`sparkline-complete`). Generate wrapper outputs from a single event manifest.

### [high] components-radial-7: Gauge data is positional and the parser filters entries, so a bad value silently corrupts value, min and max; the docs contradict each other (data-model)
- Evidence: gauge:301-303 `value = data[0]; min = data[1]; max = data[2]`; data.js:17 filters out non-finite entries so `[null, 0, 100]` becomes `[0, 100]`. docs/components/mini-gauge-chart.md:6-9 says 'single number'; README.md:107 and docs/getting-started.md:129 say `[value, min, max]`.
- Detail: Feeding a usual sparkline series such as `[10, 20, 30]` produces value=10, min=20, max=30, and the needle is pinned to min. A null value produces value=0 and min=100, after which max becomes 101 (gauge:305). The same index shifting affects pie and half-pie, where `[10, null, 5]` gives slice 2 colour-2 instead of colour-3 and breaks any external legend. Progress ignores data[1..2] while gauge honours them, so two meter components disagree.
- Rec: Introduce a typed normalisation layer: `normalizeMeter(input) -> {value, min, max, issues}` accepting `number | [number] | {value, min?, max?}`, with min and max coming only from attributes or object keys. For series, `normalizeSeries(input) -> {items: {value, label?, color?, valid}[]}` keeps index alignment, so an invalid entry becomes an invalid item rather than vanishing. Deprecate the positional `[value, min, max]` with a console warning, and document a single shape.

### [high] components-radial-8: The global token --mini-chart-stroke-width means different things in different components (theming)
- Evidence: svg.js:28 line default 2; gauge:129 `stroke-width: var(--mini-chart-stroke-width, 14)`; progress:100,106 default 12; README.md:152 lists it as a global token with default `2` for 'lines, wicks, and arcs'; docs progress default claims 10 (mini-progress-chart.md:20). Radial-bar ignores it and sets an inline px width (radial:288, 291, 345, 348).
- Detail: A dashboard theme that sets `:root { --mini-chart-stroke-width: 2.5 }`, as the README suggests, shrinks gauge tracks from 14 to 2.5 and progress arcs from 12 to 2.5. Radial-bar width can't be themed at all. A theming system needs every token to mean one thing.
- Rec: Split the tokens: keep `--mini-chart-line-width` (or the existing name) for line strokes, and add `--mini-chart-arc-width` or component-scoped tokens (`--mini-gauge-track-width`, `--mini-progress-track-width`, `--mini-radial-track-width`). Let radial-bar read its token with the computed value as fallback (`stroke-width: var(--mini-radial-track-width, <computed>)` through an inline custom property, not an inline stroke-width).

### [medium] components-radial-9: Hover events report hard-coded palette colours, ignoring --mini-chart-color-N theme overrides (theming)
- Evidence: pie:130 and half:128 `const color = getSegmentColor(index)`; radial:158 `item.color || getSegmentColor(trackIndex)`; the rendered fill uses `var(--mini-chart-color-${index+1}, …)` (pie:213, radial:297).
- Detail: After a consumer sets `--mini-chart-color-1: purple`, the slice renders purple but `sparkline-hover.detail.color` still reports `#84cc16`. Any tooltip or legend built from the event is wrong under a custom theme or dark mode. Gauge's `zoneColor` is the raw string "var(--mini-chart-safe-color, …)", which no consumer can use directly.
- Rec: Resolve the colour actually in use at event time (`getComputedStyle(target).fill` or `.stroke`, or read the per-index custom property from the host), or compute it once per render and cache it per index. Use the same detail shape in every component.

### [medium] components-radial-10: README theming example `--mini-chart-fill` has no effect on pie; per-segment theming depends on an override (theming)
- Evidence: README.md:140-143 `mini-pie-chart { --mini-chart-fill: #7c3aed; }`; svg.js:34 base rule uses `var(--mini-chart-fill, var(--mini-chart-segment-color, currentColor))` but pie:98-99 and half:96-97 redefine `fill: var(--mini-chart-segment-color, currentColor)`, and pie:213 / half:208 always set `--mini-chart-segment-color` inline.
- Detail: The single-colour override documented in the README is ignored, and so is the host `color` (currentColor is never reached). Area chart honours `--mini-chart-fill` but pie doesn't, so the same token behaves differently across the library.
- Rec: Decide on precedence explicitly. For example: `fill: var(--mini-chart-fill, var(--mini-chart-color-N, palette))`, with the per-index custom property set inline (`--_seg-color`) and resolved in the stylesheet so that `::part(segment-2)` and the tokens both win over the defaults. Fix the README to match.

### [medium] components-radial-11: Some observed attributes do nothing or only apply on the first render (pad-angle, radial min, needle-type, round-caps) (api)
- Evidence: pie:19 observes `pad-angle`, but no code reads it; radial:27 observes `min`, never read (only max at radial:233). Both are typed in React (react/index.ts:95-96, 110) and Angular (directive :299, :376) and `min` is documented (mini-radial-bar-chart.md:23). gauge:172 reads `needle-type` only in #createDOM; radial:112 `round-caps` only in #createDOM.
- Detail: Users bind these attributes through typed wrappers and nothing happens. With needle-type and round-caps the attribute does trigger a re-render (it is observed), but the value is never re-read, so the chart keeps its first-render state.
- Rec: Either implement them (pad-angle as an angular gap per slice in createRadialLayout; min as the lower bound in createRadialBarLayout; needle-type by swapping the `d` attribute on update; caps through a data-attribute selector) or remove them from observedAttributes, the types and the docs. Add a test asserting that every observed attribute changes the output.

### [medium] components-radial-12: Gauge with empty data keeps the old value text and aria-valuenow; a gauge that starts empty draws no dial (bug)
- Evidence: gauge:291-295 hides only the needle and calls `this.removeAttribute("aria-valuenow")` on the host, while the aria attributes are set on the svg (gauge:315-317); #valueText (gauge:319-324) is not hidden; zones are drawn only after the early return (gauge:332).
- Detail: Going from `[72]` to `[]` leaves '72' displayed and `aria-valuenow="72"` on the role=meter svg, which tells assistive technology a value is present. A gauge whose first render has empty data shows an empty box, with no track or zones until data arrives. Progress has the opposite problem: empty data renders as value 0 with aria-valuenow=0 (progress:237, 245), so an empty meter can't be told apart from 0%.
- Rec: Define an explicit empty state shared by all meters: draw the track and zones, hide the needle or value and the text, remove aria-valuenow from the same element it was set on (and set `aria-valuetext="No data"`). Use the same state in gauge and progress.

### [medium] components-radial-13: Gauge zones aren't clamped to [min, max], and invalid zones leave an empty gauge with no fallback (bug)
- Evidence: gauge:360-366 computes `endAngle = π + π*((zone.upTo - min)/range)` without clamping; gauge:272-274 filters entries (`Number.isFinite(z.upTo)` rejects string "50") and returns the possibly empty result; the default zones are used only when JSON parsing fails or the input array is empty (gauge:278).
- Detail: `zones='[{"upTo":150,"color":"red"}]'` with max=100 produces an arc beyond 2π that wraps below the baseline. Zones whose `upTo` values are strings (common when the data comes from forms or APIs) are all filtered out, so no track is drawn and activeZoneIdx is -1. Zones that stop short of max leave an uncoloured gap, and values in that gap are attributed to the last zone.
- Rec: Clamp each zone to [min, max], coerce numeric strings, fall back to the default zones when nothing valid remains (with a dev warning), and draw a neutral track under any gap. Give each zone a part and an optional name (`zone zone-N`, plus `name` in the zone-change detail).

### [medium] components-radial-14: Radial-bar sweep and max aren't validated: negative or >360 sweeps draw wrong arcs, and max=0 gives NaN (bug)
- Evidence: radial:236-238 accepts any degrees; geometry.js:331-349 describeArc uses `Math.abs(sweep)` but always sweep-flag 1. Verified: describeArc(50,50,44,-π/2,-π) gives 'M 50 6 A 44 44 0 0 1 6 50', an arc centred on (6,6). Sweep 400 produces a full-circle path (geometry.js:335) while progress is computed against 400° (radial:318, 350). geometry.js:443 `value / domainMax` with max="0" gives Infinity or NaN.
- Detail: A negative sweep (counter-clockwise rings) draws arcs bulging the wrong way. Sweeps above 360 desynchronise the dash offset from the path length. `max="0"` makes positive rings render full, and zero values compute NaN, so the strokeDashoffset assignment is dropped and the ring keeps its previous state.
- Rec: Clamp sweep to (0, 360] or support negative sweeps properly (derive the sweep flag from the sign). Validate max > 0, falling back to the default. Put all radial angle and validation logic in one geometry function with unit tests.

### [medium] components-radial-15: Radial-bar's default max (the largest value) always fills the largest ring, unlike progress and gauge (default 100) (data-model)
- Evidence: geometry.js:434 `domainMax = maxDomain ?? Math.max(...values, 1)`; docs radial.md:24; demo/app.js:491-492 renders 'Activity goal rings' `[75,55,90]` with no max, so 90 shows as 100% and 75 as 83%. progress:233 and gauge:303 default to 100.
- Detail: For an 'activity ring' or goal metaphor this silently misrepresents the data. The three meter-like components use three different default domains, which works against a coherent data model. `Math.max(...values)` also throws a RangeError for very large arrays (over about 100k values).
- Rec: Default to 0..100, matching progress and gauge, and require an explicit `max="auto"` for data-relative scaling. Compute the max with a loop instead of spreading. Share one `resolveDomain()` helper across all meter components.

### [medium] components-radial-16: Pie and half-pie: a dominant slice above about 99.9998% disappears because of coordinate rounding (bug)
- Evidence: geometry.js:269 full-circle threshold `sweep >= TAU - 1e-6`; geometry.js:297-305 single-arc sector; geometry.js:354-357 rounds to 3 decimals. Verified with node: data [1e6, 1] gives slice 0 = 'M 50 50 L 50 2 A 48 48 0 1 1 50 2 Z' (identical arc endpoints, which the SVG spec says to omit). The near-full donut gives 'M 50 2 A 48 48 0 1 1 50 2 …'.
- Detail: When the residual sweep is above EPSILON but the chord is shorter than 0.0005 units, the start and end coordinates round to the same point and the renderer drops the arc. The 99.9999% slice then draws as a zero-area wedge and the pie looks almost empty. Any arc spanning close to 360° is fragile in the same way.
- Rec: Draw any arc with sweep > π as two arcs, split at the midpoint, so the endpoints never coincide. Alternatively, base the full-circle test on rendered precision (chord < 10^-3), not on radians. Add property tests for extreme ratios.

### [medium] components-radial-17: Zero-sum, all-negative or all-zero data renders a blank chart with no empty state; negatives are clamped silently (data-model)
- Evidence: geometry.js:239-246 clamps negatives to 0 and gives zero sweep when total=0; describePieSector returns "" (geometry.js:267); pie:199-202 sets d="" and returns early, also skipping the data-index and part refresh, so stale attributes from the previous render remain. Verified: [0,0] gives ['',''] and [-3,5] gives ['', full circle].
- Detail: `[0,0,0]` shows nothing, while the accessible label claims 'Pie chart with 3 values'. Negative inputs vanish with no warning. Because of the early return, a segment that was index 1 keeps `part="segment segment-2"` and its colour after becoming empty. That is mostly harmless now, but fragile.
- Rec: Render a neutral track ring or half-ring as the empty or zero-sum state (part `empty`, with an `--mini-chart-empty-color` token). Expose how negatives are handled (document the clamp, or offer an `absolute` mode). Always update part and data-index before deciding a path is empty. Update the default label to describe the empty or zero state.

### [medium] components-radial-18: The `donut` attribute does nothing when used as a boolean, and donut and inner-radius are redundant synonyms (api)
- Evidence: pie:177 and half:172 `parseFloat(getAttribute("donut") || getAttribute("inner-radius") || "0")`: an empty-string `donut` falls through to inner-radius and then to 0. The demo copy uses a bare `donut` (demo/app.js:257). Clamped to 0.9 (pie:178). React types `donut?: number` (react/index.ts:93).
- Detail: `<mini-pie-chart donut>` renders a solid pie. `inner-radius="20"`, a natural reading as an absolute radius, is clamped to a 0.9 ratio and produces a hairline ring. Two attributes control the same thing and the ratio semantics are documented nowhere.
- Rec: Keep a single `inner-radius` (a ratio from 0 to 1, documented) and make bare `donut` mean a default ratio (e.g. 0.6). Deprecate the duplicate with a warning, and give the property a typed accessor.

### [medium] components-radial-19: Pie and half-pie are about 85% duplicate code, and helpers are copy-pasted across the radial group (duplication)
- Evidence: `diff mini-pie-chart.js mini-half-pie-chart.js` shows only 39 differing lines out of about 230. The gradient parsers in progress:205-220 and gauge:243-259 are identical except for the default stops; radial:191-211 is a variant; bullet has a fourth copy. Listener plumbing is repeated in all 5 (pie:121-155 etc.). None of the 5 uses `MiniChartElement.render()` (mini-chart-element.js:83-92).
- Detail: Every bug above has to be fixed 2 to 5 times, and behaviour has already drifted. Radial-bar accepts nested gradient arrays and requires at least 2 CSV colours; the others don't. Gauge caches gradients by signature; progress and radial-bar rebuild them on every render. The base class's render contract is unused by every stateful component, so the abstraction offers no shared lifecycle.
- Rec: Merge pie and half-pie into one implementation (half-pie becomes a preset with `sweep=180` and `start-angle=180`, or a subclass that only overrides layout constants). Extract shared modules: `gradient.js` (parse, plus a signature-cached `<linearGradient>` sync), `interaction.js`, `animation.js`, and a `StatefulChartElement` base with `createSkeleton()` and `update()` hooks that replace the copied `#initialized` and render() code.

### [medium] components-radial-20: Inline styles and presentation attributes stop ::part and token overrides from working (theming)
- Evidence: radial:288-308 and 345-369 set `fg.style.stroke`, `style.strokeWidth` and `style.transition` inline; gauge:399, 406 and 414 set the needle transition inline (overriding the CSS at gauge:133); gauge:368-372 colours zones through the `stroke` presentation attribute and every zone shares `part="track"`; progress:272 sets `style.stroke` inline in gradient mode.
- Detail: Outer `::part(track-fg) { stroke: … }` loses to inline styles unless `!important` is used, so consumers can't recolour radial rings through CSS. Animation timing can't be customised either, because inline transitions win over `::part(needle) { transition }`. Gauge zones can only be restyled all together, since there is no `zone-N` part. Theming strategy also differs: pie's inline-custom-property approach lets ::part win; radial-bar's inline stroke doesn't.
